\section{Introduction}
\label{sec:introduction}
Recent studies show that variable-length text types are among the most commonly used column data types in \acp{DBMS}.
For example, van Renen et al~\cite{van_renen_why_2024} showed that 52.1\% of all columns in the
Amazon Redshift are of this type.
Also Vogelsgesang et al.~\cite{vogelsgesang_get_2018} showed with their analysis of Public Tableau
Workbooks that 48.8\% of their columns are of type text.
Most interestingly, these columns not only occur frequently but are also commonly used in operators and expressions.
For example, a workload analysis of the Snowflake Data Cloud performed by Szlang et al.~\cite{szlang_workload_2025}
shows that in Snowflake BI workloads, 46\% of join keys, 58\% of filter columns contain variable-length text data.

The reason why strings are so prevalent is that they are a catch-all type for many
different kinds of data and allow a very pragmatic schema design~\cite{vogelsgesang_get_2018}.
However, this often results in data being stored in formats that are inefficient for storage and processing~\cite{vogelsgesang_get_2018}.
For example, numeric data or dates are often stored as strings instead of their native types, leading to increased storage
and processing costs\cite{vogelsgesang_get_2018}.

This prevalence of variable-length text columns poses significant challenges for query processing and storage management.
Unlike fixed-length numeric or boolean types, strings require dynamic memory allocation and incur higher CPU costs during
standard operations like comparison and hashing.
Also, their variable length makes SIMD optimizations more difficult~\cite{NEEDED}.

In this paper, we analyze how variable-length text columns are used in \acp{DBMS} and how they affect system performance
in execution and compression.
We argue that, to adequately address the heterogeneity of the data these columns can represent, it is necessary to
classify strings according to their semantic type.
Doing this, we create a \textit{taxonomy of variable-length text columns} by using \acp{LLM} to categorize string
columns as Numeric, Categorical, FullText, Identifier, Entity, or Structured.
We show that which each of these classes we can see distinct physical characteristics
(length, character distribution) and usage patterns in query execution that can be exploited for efficient storage and
query processing.


\begin{enumerate}
    \item[(RQ1)] Is there an effective and meaningful way to classify variable-length text columns based on their semantic type?
    \item[(RQ2)] What characteristic physical properties distinguish variable-length text columns across different semantic groups?
    \item[(RQ3)] How are variable-length text columns distributed across real-world databases, and what share of storage (uncompressed and compressed) does each type account for?
    \item[(RQ4)] How are variable-length text columns used in real-world analytical and transactional workloads, and which operators and execution patterns dominate their processing?
    \item[(RQ5)] Do existing benchmarks like TPC-H and TPC-DS adequately represent the diversity and characteristics of variable-length text columns found in real-world databases?
    \item[(RQ6)] Based on our findings, what recommendations can we provide for the design of future database systems and benchmarks to better handle variable-length text columns?
\end{enumerate}

As the data basis for answering these research questions, we draw on queries, schema information, and data from
publicly available repositories by extending the SchemaPile dataset~\cite{dohmen_schemapile_2024} and combining it with
datasets from Kaggle and HuggingFace to form \textit{DBPile}, as described in \cref{sec:data-collection}.
Our work differs from previous studies such as~\cite{van_renen_why_2024, vogelsgesang_get_2018, szlang_workload_2025}
in that we also release this dataset containing detailed information about the analyzed tables, columns, values, queries,
query execution traces, column usages, and compression results.

\section{Introducing DBPile}\label{sec:data-collection}

As outlined before, variable-length text columns are very heterogeneous and can have a wide range of properties.
To quantitatively analyze and understand their properties and usages, we need a dataset that contains many
real-world database schemas, queries, and sufficiently populated tables.
So far, there is no such dataset publicly available that meets these requirements.
While the studies on the Snowflake Data Cloud~\cite{szlang_workload_2025} and Amazon Redshift~\cite{van_renen_why_2024}
analyze real-world workloads; however, the underlying data is not publicly available.

One publicly available dataset that offers over 200k schemas is SchemaPile~\cite{dohmen_schemapile_2024}, a collection
of database schemas extracted from DDL and DML statements found in SQL files across public code repositories.
However, as this dataset only contains the schema information together with data retrieved from insert statements.
This leads to a table only containing 27.6 values on average.
In addition, SchemaPile only provides schema and table information and limit data in the tables, but no \texttt{SELECT} statements.

One other source of publicly available generated datasets is the TPC benchmark suite.
Combining the SELECT statements from TPC-H and TPC-DS leads to a total of 22 + 99 = 121 queries on 8 + 24 = 32 tables, which is too small for a comprehensive analysis.
One additional point of criticism that we already anticipate here but will discuss later is that the text from the columns is very unrealistic.
For example, the \texttt{customer.c\_name} has the format \texttt{Customer\#0000000X}, while the \texttt{customer.c\_address} contains random strings of characters.
Therefore, we cannot use these datasets as our baseline for analyzing string properties.
On the contrary, we will compare our findings against these benchmarks later in the paper to recommend improvements for future benchmark designs.

Another benchmark available on real-world data is the Join Order Benchmark~\cite{leis_how_2015}, which uses the IMDB dataset.
This benchmark features 113 queries on 21 tables, not enough for a comprehensive analysis.

A recent benchmark published is SQLStorm~\cite{schmidt_sqlstorm_2025}.
SQLStorm v1.0 features over 18 K \ac{LLM}-generated queries on the Stack Overflow dataset, 11 K queries on the IMDB dataset, 17 K queries on TPC-H, and 15 K queries on TPC-DS, totalizing to over 61 K queries on four different datasets.
While this benchmark is great for analyzing a lot of different query patterns, for our use case the number of different datasets is too small.
For DBPile, we included SQLStorm as a reference dataset to compare the characteristics of string columns and their usage patterns against the other datasets.

In addition, there are publicly available datasets used for ML and AI applications on platforms like Kaggle and HuggingFace.
Kaggle, in particular, features many datasets as a single denormalized table, with 4k stored as parquet and 251k stored as CSV. In addition,
there are 379 not denormalized datasets available as SQLite databases and 84 as BigQuery datasets.
HuggingFace features over 300k datasets stored as parquet.
The problem with these datasets is that they usually do not come with queries and that they are normalized, meaning that
they usually contain only a single (wide) table.

In order to create a dataset that meets our requirements, we decided to combine multiple data sources.
First, we extended the SchemaPile dataset by rescraping the original repositories to extract all SQL statements, including \texttt{SELECT} statements, as
outlined in \cref{subsec:sqlpile-dataset}.
This way, we have schemas and queries; however, the tables are still sparsely populated.
Because of this we also add datasets from Kaggle and HuggingFace, as outlined in \cref{subsec:kaggle-datasets}.
We aim to use the first to analyze the usage of string columns in queries, while we use the latter to analyze the properties of string columns in populated tables.
As refrence datasets, we also include TPC-H, TPC-DS, and SQLStorm in DBPile to compare our findings against well-known benchmarks.

Using this combination of dataset, we created a taxonomy of variable-length text columns in \cref{sec:semantic-type}
and analyzed their properties in \cref{sec:string-properties}, storage characteristics in \cref{sec:storage},
and query processing patterns in \cref{sec:query-processing}.

\subsection{Dataset Content and Schema}\label{subsec:data-collection-pipeline}

An abstracted overview of the DBPile schema is shown in \cref{fig:figure}.
The basic building blocks of the dataset are \texttt{Repositories}, for which we store the queries contained in them.
For repositories coming from SchemaPile, we scrape all code files as explained in \cref{subsec:sqlpile-dataset}.
For benchmark datasets like TPC-H, TPC-DS, and SQLStorm, we retrieve the queries from their repositories.
The DDL and DML statements are then parsed to extract the \texttt{Tables} and \texttt{Columns} contained in them.
To analyze one repository, we first create the database schema by creating all tables and populating them with the data.
Then we execute all \texttt{SELECT} statements found in the repository and store their \texttt{QueryPlans} and
\texttt{QueryResults}.
After populating the tables, we determine the semantic type of all variable-length text columns
as described in \cref{sec:semantic-type}.
For all columns of all tables, we also store 5000 sampled \texttt{Values} and analyze their
Properties based on up to 122.880 sampled values per column.
Finally, we also store the results of compressing the column in blocks of 122.880 values with different compression algorithms.

\section{A taxonomy of String Columns}\label{sec:semantic-type}
Variable-length text columns are a catch-all type for many different kinds of data.
To understand what users
of \ac{DBMS} store in these columns and how they use them, we need to understand what these columns represent.
In this section, we present a taxonomy of variable-length text columns based on their semantic type.

\input{assets/table_semantic_types}
Our taxonomy design was guided by four goals: (1) intuitive categories that reflect real-world use cases,
(2) minimal category count, (3) mutual exclusivity, and (4) high coverage without overreliance on an `Other` category.

We developed our taxonomy through an iterative process.
By examining samples of columns from our dataset, we repeatedly refined an initial set of manually
defined categories until we achieved both high coverage and clear boundaries with as few categories as possible.
The resulting taxonomy consists of six groups, each reflecting a distinct semantic type that captures the
majority of use cases observed in our data: Numeric, Category, FullText, Identifier, Entity, and Semi-structured.

In addition, we added a \texttt{Test} type to capture columns that are only used for testing purposes.
With the data coming from public repositories, we found a significant number of such columns we wanted to exclude from the analysis.
To further classify the columns, we defined subcategories for each type that capture more specific use cases.
All types and their description are summarized in \cref{tab:semantic-types}.

\subsection{Semantic Type Pipeline}\label{sec:semantic-type-pipeline}
To classify text columns into semantic types, we used an \ac{LLM} (Qwen3.5 via Ollama, \texttt{qwen3:8b}) to assign a single semantic label to every text column.
For each candidate column we collected up to ten \emph{distinct, non-empty} sample values for the classification.
To keep the prompts compact, the concatenated examples per column were truncated to a maximum length of \(\leq 200\) characters.

With the type descriptions from \cref{tab:semantic-types}, we constructed the following system prompt:
\begin{quote}
    \small
    \texttt{Based on the table name, column name, and sample values, determine the semantic type of each column.
    Every column must fit one of the types:}\\
    \texttt{<type\_1>} \texttt{<type\_1\_description>}\\
    \(\dots\)\\
    \texttt{<type\_N>} \texttt{<type\_N\_description>}\\
    \texttt{You will be given multiple columns at once.
    Return *only* the list of semantic types in the same order as the columns were provided.}
\end{quote}
Then, we batch five columns per prompt and constructed the user prompt as follows:
\begin{quote}
    \small
    \texttt{Determine the semantic type for each of the following columns:}\\
    \texttt{Column 1:}\\
    \texttt{Table: <table\_name>}\\
    \texttt{Column: <column\_name>}\\
    \texttt{Sample Values: [v\_1,\dots,v\_k]}\\
    \(\dots\)\\
    \texttt{Column N: \dots}
\end{quote}

After categorizing all columns into the base types, we performed a second classification step to assign subcategories using the same approach.

\begin{itemize}
    \item  Based on the analysis, we created a benchmark for strings.
    \item  What columns compress how well with which compression algorithm?
    \item  What are the expensive parts for e.g. a join operation of a int64 compared to a string?
    \item The goal should be to have a benchmark where both the compression and the execution can be tested.
    So the data is allowed to be compressed by the DBMS, the idea is to leverage how the data is compressed for execution.
    -> String processing is manly compressed execution
    \item The benchmark should measure compression speed, compression ratio, and execution speed, a bit similar then
    Clickbench but not with obscure queries then can be easily exploited on.

The idea for creating the benchmark is to get kaggle datasets (mainly ml datasets). They are usually denomalized single
tables so we could LLMs to normalize the data a bit more. Then we could use LLMs to generate very simple queries with
not that many joins. The benchmark should not be winable by good join ordering, but really focus on core operator
speed and the leverage of compression.
The problem of SQLstorm for string execution lays in the complexity of the queries. This means that good
query optimization will overshadow the actual execution performance.

\section{Findings}\label{sec:findings}
While the TPC-H schema defines a \texttt{comment} column for all tables
(e.g., \texttt{l\_comment}, \texttt{o\_comment}), only \texttt{c\_comment},
\texttt{o\_comment}, and \texttt{s\_comment} are actually used
This is especially noteworthy as also the comments from high cardinality tables like \texttt{lineitem} are not used.

Similar for TPC-DS, we only two out of five comment columns are used (\texttt{item\_desc} and \texttt{reason\_desc}).


\section{Limitations}\label{sec:limitations}
\begin{itemize}
    \item SQLPile contains a lot of simple queries. Many queries come not from suffisticated industrial applications, but
    from small personal projects.
    \item We only have a limited number of queries with joins and aggregations.
    \item While SQLPile contains mainly OLTP queries and schemas, kaggle are OLAP/ML datasets. We assume the properties of strings with
    the same semantic type are similar in both workloads.
\end{itemize}


\section{Recommendations for future Research}\label{sec:recommendations-for-future-research}

\begin{itemize}
    \item Strings are a catch it all type. We should not treat them as a single type, but accept that with differnt
    semantics come different properties that need to be treated differently.
    \item It is worth to do this, as strings are a significant part of the data stored and processed in DBMS.
\end{itemize}
